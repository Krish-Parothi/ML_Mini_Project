Viva Voce Defense & Architectural Justification

Curated justifications, mathematical rationale, and answers for examiner viva questions.

QUESTION 1 • DATASET SELECTION

Why was the PhiUSIIL Phishing URL Dataset chosen over legacy datasets like Mendeley or PhishTank raw lists?

Justification: Legacy phishing datasets often contain severe limitations: (1) small sample sizes (<10k rows) causing overfitting, (2) synthetic or non-representative balance, and (3) only lexical strings without web topological features. PhiUSIIL (235,795 verified URLs) integrates 54 multi-dimensional features spanning lexical composition, character continuation rate, domain entropy, external references, and webpage DOM traits, reflecting modern spear-phishing attack vectors.

QUESTION 2 • DATA LEAKAGE MITIGATION

How was data leakage strictly prevented during data preprocessing and scaling?

Justification: Data leakage occurs when test set statistics influence training. We enforced strict pipeline boundaries: (1) Identifier/free-text fields (FILENAME, URL, Domain, Title) were purged prior to numerical ingestion, (2) Stratified train-val-test splitting (65% train, 15% validation, 20% test) was performed prior to scaling, and (3) The StandardScaler was fitted strictly on the training partition and merely transformed on validation and test sets.

QUESTION 3 • METRIC JUSTIFICATION

Why is Recall (Sensitivity) prioritized over Accuracy in phishing URL classification?

Justification: In cybersecurity threat detection, the asymmetric cost of errors is severe. A False Negative (classifying a phishing link as safe) leads to credential theft, malware infection, and financial compromise. A False Positive merely causes a user prompt or temporary block. Therefore, Recall for the phishing class ($TP / (TP + FN)$) must approach 100% to guarantee zero malicious URLs bypass the gateway.

QUESTION 4 • MODEL ARCHITECTURE CHOICE

Why did LightGBM and XGBoost outperform Logistic Regression and Deep Learning on this task?

Justification: Tabular cybersecurity features exhibit non-linear boundaries, heterogeneous scales, and complex interaction terms (e.g. IsDomainIP interacting with HasPasswordField). Gradient Boosted Decision Trees (GBDT) naturally partition feature space hierarchically without requiring continuous manifold assumptions, handles correlated features robustly, and computes inference in 0.005 ms/sample, compared to deep neural networks which require massive parameter overhead and GPU inference.

QUESTION 5 • PRODUCTION DEPLOYABILITY

How does this architecture ensure cross-platform accessibility and real-time browser speed?

Justification: The backend is implemented as a lightweight FastAPI asynchronous server serving serialized .joblib models with an in-memory memory footprint under 50MB. Real-time URL feature extraction executes in < 0.5ms. The cross-platform UI is fully responsive across desktop, tablet, and mobile devices, and communicates via standard REST APIs, making it drop-in compatible with Chrome/Firefox browser extensions and enterprise email security gateways.

QUESTION 6 • OUTLIER & IMBALANCE HANDLING

How were outliers and class distribution handled?

Justification: We conducted Interquartile Range (IQR) and Z-score outlier audits across continuous features like URLLength and LineOfCode. While extreme values represent real-world obfuscated attacks (e.g., 200+ character URLs), tree-based architectures are inherently invariant to monotonic feature transformations. Stratified K-fold sampling ensured the 42.7% phishing vs. 57.3% legitimate class distribution was rigorously maintained across all partitions.
